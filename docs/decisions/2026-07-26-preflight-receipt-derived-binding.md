# Live Preflight Binds Through the Receipt Contract, Not Through Pinned Literals

Date: 2026-07-26
Status: LOCKED FOR IMPLEMENTATION; NOT IMPLEMENTED, NOT LIVE-VERIFIED
Braincrew decision baseline: `97fad79` (`origin/develop`)
AX applied baseline: `2bcaee3495fd7b3f624398819575cd86a5a15c47` (the commit AX-B ran at)
Supersedes in part: [`docs/decisions/2026-07-24-ax-evaluation-principal-and-parse-restoration-scope-lock.md`](./2026-07-24-ax-evaluation-principal-and-parse-restoration-scope-lock.md)

This record supersedes exactly one operative element: **how `live_preflight` learns the evaluation
principal and the case-to-attachment mapping.** Every other locked element — dataset versions, the
approval triple, provider lineage, count deltas, failure codes, provenance representation, and
operational gating — remains in force unchanged.

## 1. Decision

**Braincrew Issue #38's recorded "receipt consumer only" role is a binding architectural
commitment**, not a description. The live preflight therefore derives the evaluation principal and
the case-to-attachment mapping from the AX handoff receipt, and pins **one** value instead of seven:
the reviewed receipt's SHA-256.

```text
before   seven literals pinned in live_preflight.py
           ACTIVE_OWNER_USER_ID                = 22222222-…
           REVIEWED_PARSING_ATTACHMENT_IDS[6]  = 2c7d525b-… … 569dc67a-…

after    one literal pinned in live_preflight.py
           REVIEWED_HANDOFF_RECEIPT_SHA256     = <digest of the independently reviewed receipt>
         everything else derived from the receipt that hashes to it
```

The receipt path is a run-time input, like the bundle directory. **The receipt is not copied into
this repository**; it is create-only operational evidence living outside both repositories, and
duplicating it would create a second artifact that could drift from the reviewed one.

## 2. Why the pinned literals could never be right

The measurement on 2026-07-26, against the applied corpus:

| Pinned value | Live reality |
| --- | --- |
| `ACTIVE_OWNER_USER_ID = 22222222-…` | `executive@hanbit.example`, tenant `11111111-…` — a demo Executive in a **different tenant**, never an evaluation principal |
| six attachment UUIDs | **zero of six** exist |

This is not drift. **AX generates attachment IDs and the contract forbids caller-forcing them** — the
Stage 11 verification states the version-set placeholders "are resolved only from the six receipt
approval IDs generated by AX; they must never be caller-forced." A literal that names an
AX-generated identifier is therefore wrong at authoring time and stays wrong. It was wrong before
AX-A existed and it is wrong after AX-B ran.

Re-running the apply to regenerate matching identifiers is **forbidden and would not work**:
`AttachmentService.stage_files` de-duplicates by content hash within a thread, so a retry returns the
existing IDs and creates no rows — a silent fake success.

## 3. The anti-tautology control, which is the whole point

The obvious cheap implementation — read the current database, harvest whatever attachment IDs it
holds, then verify against them — **would go green while proving only that the code can read its own
inputs.** It is the same failure mode this project has now met three times:

| Occurrence | Shape |
| --- | --- |
| `inventory.regen.json` | a non-conforming generator compared against itself |
| Stage 9 `cmp -s` | two runs of the same script by the same party |
| this decision, avoided | a mapping harvested from live state and compared to live state |

What separates a receipt-derived binding from that tautology is **not** that the values come from a
file. It is that the file's digest was **reviewed and committed before the observation happens**:

- the receipt is **create-only** and was written once by the apply;
- it passed **independent review** — Stage 11 returned `PASS` and bound its digests;
- its SHA-256 is committed into Braincrew source, so the mapping's authority is fixed in advance;
- at run time the preflight recomputes that digest and **refuses on mismatch**.

**Binding the digest is the control. Reading the file is not.** An implementation that reads the
receipt without verifying its digest has all of (B)'s complexity and none of its safety, and must be
rejected in review.

## 4. Rejected alternatives

**(A) Re-pin the seven literals to today's values.** Rejected. It buys one green run and re-arms the
same failure: any future provisioning invalidates them again, because the identifiers are
AX-generated by contract. It also leaves the category error intact — the owner constant would be
right by accident of today's data rather than right by construction. It contradicts the
receipt-consumer-only commitment this decision confirms as binding.

**Harvest the mapping from the database at run time.** Rejected as the tautology in section 3.

**Add a caller-forced attachment ID to AX so Braincrew's literals can be honoured.** Rejected. It
weakens a safety property in the system under test to make a flag flip, and `AGENTS.md` limits AX
work to narrowly scoped changes that unblock evaluation — this would be neither narrow nor a fix.

**Commit a copy of the receipt into this repository.** Rejected. Two copies can diverge, and the
reviewed one is the evidence-root original. Pinning its digest gives the same guarantee without the
duplicate.

**Fold the SUT commit re-pin into this change.** Rejected — see section 5.

## 5. What this decision deliberately does not settle

**`PINNED_AX_SHA` remains a separate, separately reviewed decision.** The receipt carries
`repository.commit_sha = 2bcaee34…`, so it is tempting to derive that too. It should not be, because
the two values are **different assertions**:

- `receipt.repository.commit_sha` is an **observed fact** — the commit AX-B happened to run at;
- `PINNED_AX_SHA` is a **Braincrew-side review decision** — the SUT commit this evaluation plane has
  reviewed and accepts.

Requiring `receipt.repository.commit_sha == PINNED_AX_SHA` is therefore a real check that fails when
someone presents a receipt produced at an unreviewed commit. Deriving one from the other would
delete that check while appearing to simplify.

The current value `72805930…` is a genuine ancestor of the applied commit — superseded, not
fictional — and is enforced in the `LivePreflightArtifact` validator, so **no artifact captured
against today's substrate can currently be constructed.** Re-pinning it touches 36 occurrences across
13 files, several of them contract tests, and requires answering a question nobody has yet asked:
`2bcaee34…` was reviewed as the **provisioning** execution commit; it has not been reviewed as the
SUT commit **for evaluation**. That review is in scope for a separate change and is not performed
here.

**`FROZEN_DATASET_VERSION = "2.0.0"` is explicitly out of scope.** It sits beside an AX corpus
labelled `braincrew-evaluation-dataset-3.0.0`, which is a **name collision, not a mismatch** — the
preflight validates Braincrew's own manifest, and v2 maps to `parsing_cases_v1`, whose canonical text
for cases 015–020 is byte-identical to the AX-B bundle. A sweep that "updates the stale constants"
would plausibly bump this one and silently re-point the evaluation plane at a different case set.

## 6. Identifiers: two sets doing two jobs

Any implementation that treats "the six UUIDs" as one thing will fix the wrong half.

| Identifier | Role | Where it is used |
| --- | --- | --- |
| `attachment_id` | **probe address** — what to call to observe parsing of case X | the preflight mapping; `response.attachment_id` mismatch raises |
| `approval_id` | **provenance stamp** — under which approval the row entered the corpus | `created_by_seed_version = "tenant-upload-v1:<approval_id>"` on materialized rows |

The two sets are disjoint. This decision changes only how the **attachment** mapping is obtained. The
approval IDs are already consumed correctly from the receipt by Stage 11 and are untouched.

## 7. Failure modes this must handle

| Condition | Required behaviour |
| --- | --- |
| receipt file absent or unreadable | fail closed, distinct error; never fall back to literals |
| receipt digest ≠ pinned digest | fail closed; this is the anti-tautology control firing |
| `state != "COMPLETED"` or `completion_confirmed != true` | fail closed |
| receipt `repository.commit_sha` ≠ `PINNED_AX_SHA` | fail closed — unreviewed SUT commit |
| receipt contains other than six attachments | fail closed |
| a reviewed case id missing from the receipt mapping | fail closed; no partial mapping |
| receipt `target.subject_id` not active in the receipt's tenant | fail closed |

No condition may degrade to a warning, and none may fall back to the previous literals — a fallback
would silently restore the behaviour this decision removes.

## 8. Validation evidence available, and what is still missing

**Available now.** The receipt exists, is create-only, passed Stage 11 independent review with digest
bound, and carries every value this design consumes: `target.subject_id`, the ordered six
`case_id → attachment_id` mapping, `repository.commit_sha`, `bundle.manifest_digest`, and its own
`logical_digest`.

**Missing.** `live_preflight` captures **live HTTP** parse observations, and the AX runtime is
stopped by Stage 12. **Neither this design nor any alternative can be validated end to end without a
separately authorized runtime start.** Implementation and its controlled tests can proceed without
one; the live capture cannot.

## 9. What a `true` flag would still have to prove

Recorded so that a future change cannot lower the bar by making the pins resolve:

1. a live AX runtime answered real parse probes, not a fixture;
2. the evaluation principal was **accepted and authorized for parsing**, as a principal chosen for
   that purpose;
3. the six reviewed sources parsed to the **frozen expected evidence**, not merely to something;
4. the capture was bound to a reviewed, pinned SUT commit;
5. the captured artifact passed independent review.

`braincrew_preflight_ready` is a prose claim, not a computed value — it appears nowhere in `src/`.
Making it `true` is an assertion about evidence, and this decision supplies only the mechanism for
items 3 and 4.

## 10. Likely follow-up questions

**"Isn't deriving from a file just moving the hardcoding?"** No — what is pinned changes from seven
values that are wrong by construction to one digest that is verifiable. The digest is checked at run
time; the literals never were.

**"Why not derive the SUT commit too, since the receipt has it?"** Because it would delete a real
check. See section 5.

**"Isn't this abstraction for a single use case?"** The strongest argument against. It is accepted
because the receipt-consumer-only role is already the recorded architecture and the SUT Adapter
contract is already the documented connection between the repositories — this makes the code match a
design that is already written down, rather than anticipating a hypothetical future.

**"What if the receipt is regenerated?"** It cannot be. It is create-only, and re-running the apply
is forbidden by the rerun trap. A genuinely new provisioning would produce a new receipt requiring a
new independent review and a new pinned digest — which is the intended workflow, not a defect.
