- 검토일: 2026-07-18 (KST)
- 범위: 사용자가 지정한 [Braincrew 채용 공고](https://brain-crew.com/apply/ai-research-engineer-data)와 [실밸개발자 발표 영상](https://www.youtube.com/watch?v=ViJxFYuVcfs)만 사용
- 증거 수준: 채용 페이지 원문 HTML, YouTube 게시자 설명·챕터·한국어 자동 자막. 자동 자막의 고유명사와 일부 문장은 오인식 가능성이 있다.

## 결론

빠르게 준비할 포트폴리오의 최우선안은 **문서 파싱 → RAG 답변 → 평가·비교 → 품질 모니터링**을 하나의 재현 가능한 실험으로 보여주는 `RAG/Agent Evaluation Workbench`다. 완성도 높은 범용 챗봇보다, 작은 실제 문서 세트와 직접 만든 벤치마크로 두 가지 파이프라인을 비교하고 실패 사례·개선 효과를 숫자로 설명하는 편이 공고와 더 직접적으로 맞는다.

최소 제출물은 다음이면 충분하다.

1. 공개 문서 기반의 작은 평가 데이터셋: 질문, 정답/근거 구간, 난이도·실패 유형 태그
2. baseline과 개선안 1개: 예를 들어 기본 RAG 대 reranker/질의 분해/agentic retrieval 중 하나
3. 검색·답변·비용/지연시간 지표와 실패 분석
4. 한 명령으로 재현되는 실험, 결과 표, 2~3분 데모
5. `왜 이 문제인가 → 무엇으로 채점했나 → 어떤 실험이 개선했나 → 비즈니스에 어떤 의미인가` 순서의 README

이는 공고가 명시한 평가 지표, 벤치마크 데이터셋, RAG/Agent 품질 모니터링, 최신 방법론의 파이프라인 적용, 비즈니스 요구 해결을 한 프로젝트 안에서 모두 입증한다. [채용 공고](https://brain-crew.com/apply/ai-research-engineer-data)

## 1. Data 역할: 출처 사실

### 회사·문제 맥락

- Data 팀은 문서 파싱, RAG, Agent 등 Braincrew 제품의 품질을 **숫자로 측정하는 평가 체계**를 만든다.
- 리서치에 머무르지 않고 공개 방법론을 자사 상황에 맞게 평가·적용하여 실제 비즈니스 가치를 만드는 AI 엔지니어링을 지향한다.
- 경력·학력은 무관하며, 경력보다 배우는 태도와 속도를 강조한다.
- 회사 전체 비전은 AI로 인간 역량을 증대하고 복잡한 문제를 해결하며, 고객 맞춤형 솔루션으로 비즈니스 프로세스와 경쟁력을 개선하는 것이다. [채용 공고](https://brain-crew.com/apply/ai-research-engineer-data), [회사 공식 홈페이지](https://www.brain-crew.com/)

### 명시된 책임

- 평가 지표 정의 및 벤치마크 데이터셋 제작
- RAG/Agent 평가 체계 구축과 품질 모니터링
- 공개 방법론·최신 연구의 Braincrew 파이프라인 적용 및 고도화
- 프로덕트·비즈니스 요구사항의 AI 엔지니어링 해결
- 문서 파싱·RAG·Agent 품질을 수치화하고, 실험 루틴으로 전체 품질 향상 [채용 공고](https://brain-crew.com/apply/ai-research-engineer-data)

### 명시된 자격·우대와 기술 범위

- 필수 수준: LLM, RAG, 벡터 검색의 기본 개념을 설명할 수 있음; 데이터 수집·정제·분석에 거부감이 없음.
- 행동 기준: 새 기술을 직접 써보고 자사 적용점을 찾음; 형식·절차보다 속도·실행을 중시함; 모르는 것을 인정하고 배운 것을 바로 공유함; 스스로 궁금한 것을 탐구하고 완벽한 보고서보다 빠른 실험 결과를 선호함.
- 우대: AI 프로젝트, RAG/Agent 직접 구축·사용, 모델 경량화·추론 최적화 관심/경험, AI 학회 논문 게재.
- 페이지의 구조화된 `JobPosting` 메타데이터는 기술 키워드로 `LLM, RAG, AI Agent, 벡터 검색, 평가 데이터셋, 벤치마크, Python`을 기재한다. 그러나 본문에는 특정 프레임워크, 벡터 DB, 클라우드, MLOps 도구가 명시되어 있지 않다. [채용 공고](https://brain-crew.com/apply/ai-research-engineer-data)

### 지원·평가 절차와 산출물

- 절차: 서류 → 실제 팀과 1주간 작은 과제 → 최종 면담.
- 서류 안내: 이력서와 포트폴리오(형식 자유). 하단 지원 문구에서는 이력서(CV)는 제출하고 GitHub·포트폴리오 링크는 선택이라고 표현한다.

- 과제는 AI를 이용해 수행하며 완성도 자체를 평가하지 않는다. **모르는 문제를 푸는 방식, 팀과의 소통, 피드백 반응**을 본다. [채용 공고](https://brain-crew.com/apply/ai-research-engineer-data)

## 2. 해커톤 발표자의 접근: 출처 사실

영상 게시자는 5,300명 중 본선 60명에 들었으며, 사람의 실작업은 이틀간 약 2~3시간, 에이전트 실행은 약 11시간이었다고 설명한다. 직접 코드를 쓰거나 읽는 대신 방향 설정, 문제·솔루션 확정, 최종 시각 검증과 제출을 맡았다고 한다. 이는 게시자 자신의 회고이며 외부 검증된 성과 자료는 이번 범위에 포함하지 않았다. [00:31–01:29](https://www.youtube.com/watch?v=ViJxFYuVcfs&t=31s), [04:31–06:19](https://www.youtube.com/watch?v=ViJxFYuVcfs&t=271s)

### A. 컨텍스트: 목표에서 역산해 재료를 설계

1. 목표를 `본선 진출`로 고정하고 필요한 컨텍스트를 역산했다.
2. 구현 프롬프트보다 먼저 해커톤 전문, 제출 구조, 심사 방식, 로그 가공 금지 같은 실격 규칙을 그대로 제공했다.
3. 에이전트에게 필요한 정보를 자신에게 인터뷰하도록 지시해 누락된 컨텍스트를 능동적으로 수집하게 했다.
4. 리서치를 즉시 시작하지 않고, 여섯 기업 담당자의 공식 영상에서 문제·인재상·미래 비전·심사 취향을 먼저 요약해 주입했다.
5. 이후 IR, 공식 기사, 기술 블로그, 채용 공고, 고객 리뷰, 실제 숫자와 출처를 기업별로 조사했다.
6. 처음부터 3개 기업을 고르지 않고 6개 기업을 병렬 조사해 기업당 3개, 총 18개 문제 후보를 만든 뒤 비교했다. [06:21–09:05](https://www.youtube.com/watch?v=ViJxFYuVcfs&t=381s), [09:46–14:12](https://www.youtube.com/watch?v=ViJxFYuVcfs&t=586s), [14:15–17:57](https://www.youtube.com/watch?v=ViJxFYuVcfs&t=855s)

### B. 문제를 구현보다 오래 담금질

- 초기 문제와 솔루션이 약하거나 너무 쉬우면 다시 검토시켰다.
- 에이전트 시대의 생산성을 반영해 사람이 3~4주 걸릴 규모를 1~2일에 구현하는 식으로 스코프 기준을 상향했다.
- 단일 기능보다 하나의 부서 역할로 성장할 잠재력, 당장 사용할 수 있는 가치, agent-friendly 인터페이스, 사람과 AI 심사자 모두를 설득할 데모를 요구했다.
- 문제 정의와 솔루션의 일치를 반복 점검했고, 이 단계에 사람 시간의 대부분인 약 2시간을 썼다고 말한다. [18:01–22:13](https://www.youtube.com/watch?v=ViJxFYuVcfs&t=1081s)

### C. 검증: 심사자를 먼저 만들고 문제부터 채점

1. 실제 심사 구조를 역설계해 `AI judge`와 `human/practitioner judge` 두 평가 스킬을 먼저 만들었다.
2. AI judge는 근거·URL·원본 로그·재현성과 agent-friendly 문서 구조 등을, human judge는 현업 적합성·30초 훅·문제의 뾰족함·데모 첫인상 등을 보도록 차별화했다.
3. 18개 문제 각각에 두 judge를 돌려 총 36회 독립 평가하고, 문제 점수가 높은 3개 기업을 선택했다. 즉 산출물 이전에 **풀 문제 자체**를 검증했다.
4. 구현 후에는 실제 데이터/API/MCP를 사용하고, 이해관계자와 이를 사용하는 에이전트의 양쪽 관점에서 평가하며, 기준 통과까지 반복하도록 했다.
5. 7라운드 모의 심사에서 실격 위험과 사실 오류를 발견·수정했고, 마지막은 사람이 직접 산출물을 열어 첫인상·집중도·시각 품질과 `taste`를 판단했다. [22:25–27:15](https://www.youtube.com/watch?v=ViJxFYuVcfs&t=1345s), [27:17–29:44](https://www.youtube.com/watch?v=ViJxFYuVcfs&t=1637s), [29:44–32:33](https://www.youtube.com/watch?v=ViJxFYuVcfs&t=1784s)

### D. 스캐폴딩: 같은 계약으로 병렬화

- 모든 기업에 `리서치 → 문제 정의 → 솔루션 계획 → 구현 → 검증` 공통 파이프라인을 적용했다.
- 공통 프롬프트 템플릿, 스펙, 심사 스킬, 단계별 산출물 계약과 handoff 파일을 만들어 세션 간 상태를 보존했다.
- 설계·구현·평가 세션을 분리하고, 제작 맥락을 모르는 블라인드 평가자를 써 관대한 자기평가를 방지했다.
- 발표자가 정의한 사람의 역할은 코딩이 아니라 문제 정의, 의사결정, 기준 상향, 거절, 최종 taste 검증이었다. [32:36–34:16](https://www.youtube.com/watch?v=ViJxFYuVcfs&t=1956s), [34:16–37:18](https://www.youtube.com/watch?v=ViJxFYuVcfs&t=2056s), [37:21–38:44](https://www.youtube.com/watch?v=ViJxFYuVcfs&t=2241s)

## 3. 포트폴리오 적용: 추론

다음은 두 출처를 바탕으로 한 지원 전략상의 **추론**이며 회사가 직접 요구한 상세 사양은 아니다.

### 권장 프로젝트: RAG/Agent Evaluation Workbench

**문제 정의**  
문서 기반 AI 기능이 데모에서는 그럴듯해도, 문서 파싱 오류·검색 실패·근거 없는 답변을 일관되게 발견하고 비교하기 어렵다는 문제를 잡는다.

**빠른 범위**

- 도메인: 공개 문서 20~50개로 제한. 회사의 실제 내부 문제를 아는 척하지 말고, 평가 가능성이 높은 공개 규정·매뉴얼·공시 중 하나를 선택한다.
- 데이터: 30~60개 골든 질문과 근거 span, 답변 가능/불가능, 표·다단 문서·충돌 정보 등 실패 유형 태그.
- 시스템: baseline RAG + 개선안 하나만 구현.
- 지표: retrieval recall@k 또는 MRR, answer correctness/faithfulness, citation accuracy, abstention accuracy, latency·token/cost. LLM judge만 쓰지 말고 가능한 규칙/사람 샘플 평가와 함께 사용한다.
- 실험: 실패 유형별 before/after, 비용·품질 trade-off, 대표 실패 3건과 다음 실험.
- 데모: 질문 → 검색 근거 → 답변 → 평가 결과 → 실험 비교 대시보드 흐름.

**왜 적합한가**

- 채용 업무의 거의 모든 명시 항목을 한 프로젝트에서 직접 입증한다.
- 영상의 세 원칙을 복제할 수 있다: 공고·회사 문제를 컨텍스트로 고정하고, 구현 전에 평가 루브릭과 테스트셋을 만들며, 공통 실험 계약으로 pipeline variant를 반복한다.
- ‘빠른 실행’을 코드량이 아니라 좁은 문제, 명시적 기준, 재현 가능한 비교로 증명한다.

### 제출 포장

- 이력서 한 줄: `공개 문서 N건과 골든 QA N개로 RAG 평가 체계를 구축하고, [방법] 적용 전후 [핵심 지표]를 X→Y로 개선; 비용·지연시간 trade-off와 실패 유형별 분석을 재현 가능한 실험으로 공개`처럼 실제 수치가 나온 뒤 작성한다.
- README 첫 화면: 문제, 30초 데모 GIF, 핵심 지표 표, 재현 명령.
- 별도 2페이지 PDF 또는 README 섹션: `Context / Judge / Scaffolding`을 제목으로 삼아 영상 접근을 지원 직무에 맞게 변환한다.
- 의사결정 로그: 시도한 후보, 버린 이유, 모르는 점, 피드백 반영 전후를 짧게 남겨 과제 전형 평가 기준까지 선행 증명한다.
- GitHub·포트폴리오 링크는 하단 공고 문구상 선택이지만, 이 역할은 프로젝트 증거가 직접적인 평가 자료가 되므로 제출하는 편이 합리적이다.

## 4. 불확실성·충돌

- 상세 기술 스택은 공개되지 않았다. Python은 구조화된 메타데이터에만 있고, 특정 RAG 프레임워크·모델·벡터 DB를 채택하라는 근거는 없다.
- 정확한 1주 과제 주제와 채점 루브릭은 공개되지 않았다. 포트폴리오가 과제를 대체한다고 가정하면 안 된다.
- 공고 본문은 상시채용·성남 근무·주 2회 출근/3회 재택·채용인원 `0명`으로 표시한다. 구조화된 메타데이터는 `validThrough: 2026-12-31`, 서울 중구, `TELECOMMUTE`, `totalJobOpenings: 5`로 달라 실제 조건은 지원 시 확인이 필요하다.
- 서류 단계에는 이력서·포트폴리오가 적혀 있지만 지원 문구는 GitHub·포트폴리오 링크를 선택으로 표현한다.
- 영상의 5,300명/60명, 시간 사용, 7회 심사 및 점수는 발표자의 자기 보고다. 자동 자막은 숫자·도구명·고유명사를 틀릴 수 있어, 본 노트는 게시자 설명·챕터와 일치하는 범위에서만 사용했다.
